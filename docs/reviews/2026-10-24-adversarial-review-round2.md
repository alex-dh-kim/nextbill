# NextBill 문서 적대적 재리뷰 — 2차

검토일: 2026-10-24. 대상은 현재 작업 트리의 설계 문서(S=`docs/superpowers/specs/2026-10-23-nextbill-design.md`, 336줄), 구현 계획(P=`docs/superpowers/plans/2026-10-24-nextbill-v1.md`, 1295줄), 그리고 `docs/reviews/2026-10-24-review-response.md`다. P의 미커밋 수정도 포함했다. 줄 번호는 이 시점 기준이다. 앱 코드 실행 결과가 아니라 문서의 상태 전이와 계약에 대한 리뷰다.

## 판정

**이전보다 개선됐지만, 핵심 데이터·알림 계약 수정 후 착수 권고. P1 6건, P2 5건.**

사용 구간, 예약 occurrence, 저장 결과와 파생 작업 분리, 날짜 Flow, 클라우드 백업 제외, 홈 합계 분리, terminal UI state는 올바른 개선이다. 모듈 수 유지와 WorkManager 미도입은 선택 가능한 절충이다. 이번 지적은 특정 라이브러리를 쓰라는 요구가 아니라, 현재 선택으로 약속한 동작이 성립하는지에 관한 것이다.

## P1 — 구현 전에 닫아야 할 계약

### R2-1. 재부팅 후 DB 예약은 남고 OS 알람은 사라져, reconcile이 재등록을 생략한다

**위치:** P:394–403, 562–563, 643, 782, 801, 817; S ADR-4.

현재는 `existing == desired`이면 아무 작업도 하지 않는다. 예를 들어 내일 09:00 알람과 DB 예약 행을 만든 뒤 기기를 재부팅하면 OS 알람은 사라지지만 Room 행은 남는다. BOOT_COMPLETED가 동일 reconcile을 호출해도 둘이 같아서 등록하지 않는다. 늦어진 예약도 DB에만 남은 경우 `triggerAt <= now` 분기가 계속 보존한다. 기기 간 전송도 `nextbill.db`의 scheduled_reminders를 함께 가져오므로 같은 문제가 생긴다.

**수정:** 저장된 desired 상태와 현재 OS에 적용된 상태를 구분한다. BOOT/기기 복원처럼 OS 예약을 신뢰할 수 없는 경로에 명시적인 강제 재적용 모드를 둔다. 일반 편집에서는 정상적으로 지연 중인 다른 예약을 보존한다. 부팅 후 이미 시각이 지난 occurrence를 보낼지 건너뛸지도 정한다. PendingIntent 존재 여부만으로 OS 알람 존재를 증명하지 않는다.

**검증:** DB는 유지하고 FakeAlarmManager만 비운 뒤 BOOT 처리 → 미래 알람 재등록. 동일 상태의 일반 편집은 기존 알람 유지. 기기 전송으로 가져온 DB도 재등록. 현재 `rescheduleOnBoot`의 “refreshNow 호출 1회” 검사는 이 결함을 잡지 못한다.

플랫폼 근거: [AlarmManager API](https://developer.android.com/reference/android/app/AlarmManager), [알람 가이드](https://developer.android.com/develop/background-work/services/alarms).

### R2-2. 수신기 처리와 reconcile이 같은 임계 구역에 있지 않아 새 예약 삭제·중복 알림이 가능하다

**위치:** P:565–568, 787–800.

Mutex는 refresher에만 있다. ReminderHandler는 `getAll → notify → remove`를 그 밖에서 수행한다.

- H1·H2가 같은 stored를 동시에 읽으면 둘 다 notify할 수 있다. 순차 중복 테스트만으로는 부족하다.
- H1이 옛 예약을 읽은 후 편집 reconcile이 새 예약을 put하면 H1의 `remove(id)`가 새 예약까지 삭제한다.
- H1이 notify하고 remove하기 전 프로세스가 죽으면 DB에 남은 예약을 다음 시작에서 “지연 중”으로 오인할 수 있다.

**수정:** occurrence 검증·claim/consume·해당 예약 제거·다음 예약 전이를 같은 조정 경로에 둔다. 원자적 `removeIfMatches(id, occurrence/version)` 또는 DB claim을 사용하고, 수신과 reconcile의 직렬화 범위를 명시한다. DB와 OS notification을 완전한 하나의 트랜잭션으로 묶을 수 없으므로 프로세스 종료 시 중복/누락 중 어느 쪽을 허용하는지 정책을 정한다. “정확히 1회”를 무조건 보장한다고 쓰지 않는다.

**검증:** 두 handler를 barrier로 동시에 실행, old handler 일시정지→새 예약 put→old 재개, notify 직후 crash, remove 직후 crash. 새 예약이 지워지지 않고 선택한 전달 정책대로 동작해야 한다.

### R2-3. 가져오기 journal을 도입했지만 복구 완료 전 접근·쓰기 차단이 없다

**위치:** P:579–591, 651, 696, 969–970, 1219–1226.

staging을 먼저 남기는 방향은 타당하다. 그러나 시작 복구는 Application의 비동기 코루틴이고, Splash/UI는 설정 로딩만 기다린다. 편집·알림 수신·reconcile이 복구와 겹칠 수 있다. 특히 apply 실패 후 화면은 IDLE로 돌아가고 staging은 남는다. 사용자가 이후 구독을 편집하면 다음 앱 시작에서 staging 재적용이 그 변경을 덮는다. 두 번째 import나 이미 실행 중인 reconcile과의 배타성도 없다.

또한 `replaceAll`은 매번 새 id를 발급한다. “내용이 같다”는 의미의 재적용은 가능하지만, 열려 있는 NavKey·draft·예약의 id까지 안정적인 멱등성은 아니다. 같은 SavedStateHandle의 draft가 복구 전 id를 참조할 수도 있다.

**수정:** startup `Recovering/Ready/RecoveryFailed` 게이트와 import 적용 전체에 대한 배타적 조정 계약을 둔다. 복구 중·실패 후에는 관련 편집/알림 갱신을 막거나 명시적으로 복구를 끝낸 뒤 허용한다. 재발급 id에 맞춰 기존 navigation/draft/예약 상태를 무효화한다. 프로세스 재시작뿐 아니라 현재 실행 중 실패를 어떻게 마무리할지도 정한다. WorkManager 도입이 필수는 아니다.

**검증:** DB 교체 성공·설정 교체 실패 후 사용자가 편집 시도, recovery와 handler 동시 시작, import 두 번, staging 재적용 후 이전 detail/editor 복원. 사후 사용자 편집이 조용히 사라지지 않아야 한다.

### R2-4. 새 사용 구간 규칙으로 미래 시작 구독의 해지가 불가능해졌다

**위치:** P:237, 248, 258–272, 570, 1118, 1175.

미래 첫 결제일은 허용한다. 오늘 10/24에 anchor=12/01 구독을 만들면 마지막 구간 start=12/01이다. 오늘 상세에서 해지하면 `cancelledOn(10/24)`의 `date >= last.start` require에 걸린다. 사용자는 정상 UI로 도달할 수 있고 확인 대화상자에도 제한이 없다. 날짜/시간대를 뒤로 바꾼 경우에도 같은 문제가 발생한다.

**수정:** 시작 전 취소를 어떻게 표현할지 결정한다. 실제 사용 구간과 현재 활성 상태를 분리하거나 시작 전 취소 상태를 모델링하는 방법 등이 있다. 삭제로 안내하는 절충도 가능하지만 버튼·문구·반환 오류를 명시해야 한다. 임의로 end를 start에 맞추면 아직 발생하지 않은 결제를 남기는 문제가 생긴다. restore 날짜가 마지막 start보다 이전인 경우도 함께 정의한다.

**검증:** 미래 anchor 생성→오늘 해지→보관/복원, 복원 직후 시스템 날짜를 이전으로 변경→해지. 정상 액션으로 IllegalArgumentException이 새지 않아야 한다.

### R2-5. 앱이 생성한 데이터를 자기 백업 코덱이 거부할 수 있다

**위치:** P:341, 452–459, 569, 725–753, 1132, 1226.

1,000건·1900~2200년·1,000,000자 제한은 decode에만 있다. 신규 저장에 전체 구독 수 제한이 없고 날짜 검증 오류도 없다. 사용 구간 수에도 한도가 없다. 따라서 앱에서 만든 1,001건이나 범위 밖 날짜, 구간이 많아 큰 파일이 된 정상 데이터는 export 후 import가 실패할 수 있다. 1,000건 전제의 합산 안전성 설명도 실제 저장 경로와 일치하지 않는다.

**수정:** 저장/편집/복원/가져오기에 공통 불변식을 적용하거나 가져오기 제한을 정상 데이터 범위에 맞게 변경한다. 특히 크기 제한은 모든 유효 저장 상태의 encode 결과를 수용하도록 정하고, export 실패를 저장 성공으로 표시하지 않는다. 과도한 구간을 제한한다면 어떤 기준으로 사용자에게 안내할지도 필요하다.

**검증:** 최대 허용 상태를 앱 경로로 생성→encode→decode 성공, 1,001번째 등록 정책, DatePicker 경계 날짜, 긴 구간 이력, 최대 메모/이름 조합. `decode(encode(validState))` 성질을 대표 경계값에서 보장한다.

### R2-6. OS 알람과 예약 DB 사이의 실패 복구가 정의되지 않았다

**위치:** P:530–531, 562–577, 643, 797–800.

Schedule 액션은 OS 등록→DB put 순서다. OS 등록 성공 후 DB put 실패/프로세스 종료면 알람은 있지만 DB가 없어서 수신 시 stale로 버린다. 반대로 기존 알람의 전달이 이미 끝났는데 DB 행만 남으면 시작 reconcile은 이를 실제 지연 알람으로 오인해 보존한다. `runCatching`으로 실패를 삼키고 앱 시작에서 재실행하는 것만으로 복구되지 않는 경우다.

**수정:** 예약 적용의 `Pending/Applied/Consumed` 상태나 generation 등을 이용해 불완전한 적용을 재실행 가능하게 한다. DB에 있는 계획을 OS 적용의 증거로 취급하지 않는다. 취소 순서의 실패와 취소된 코루틴 재개 정책도 명시한다. 자동 재시도를 안 한다면 최소한 다음 복구 기회와 잔여 손실을 정확히 문서화한다. CancellationException은 일반 실패로 삼키지 않는다.

**검증:** schedule 성공 후 put 실패, cancel 성공 후 remove 실패, notify 후 DB 실패, 각 단계 프로세스 종료→다음 시작 복구. 정상 지연 알람 보존 테스트와 함께 통과해야 한다.

## P2 — 해당 영역 착수 전 보완

### R2-7. `@Immutable` 자동 처방이 패키지 전체 stability 선언으로 바뀌었다

**위치:** P:119의 `dev.lioracode.nextbill.core.model.*`, P:240, 1288.

`Subscription.periods: List<ActivePeriod>`의 깊은 불변성/alias 차단 계약이 없다. 패키지 전체 선언은 현재와 미래의 모든 모델을 stable로 약속한다. `kotlin.collections.*`를 제외해도 모델 자체를 stable로 선언하면 해당 모델 내부 List 문제를 검증한 셈이 되지 않는다.

**수정:** wildcard를 제거하고 확인한 타입만 allowlist에 적는다. 컬렉션의 방어적 복사·비노출·변경 금지 소유권을 정의한다. 리포트도 “추론”과 “설정으로 선언”을 구분해 기록한다.

**검증:** 외부 mutableList를 생성자에 넘긴 뒤 원본 변경으로 Subscription 값이 조용히 바뀌지 않는지 확인. [공식 문서](https://developer.android.com/develop/ui/compose/performance/stability/fix)는 stability 설정도 개발자의 계약이며 실제 불변성을 만들어 주지 않는다고 설명한다.

### R2-8. 캘린더의 해지 구독 결제를 누르면 상세가 즉시 닫힌다

**위치:** P:1047, 1063, 1170–1174.

캘린더는 해지 전 결제를 보존하고 모든 행에서 DetailNavKey로 이동한다. 그러나 상세는 CANCELLED이면 곧바로 Closed다. 이미 보존된 과거 결제 행을 탭해도 아무 내용을 볼 수 없다.

**수정:** 해지 구독 읽기 전용 상세를 지원하거나, 해당 행의 이동을 제거하고 정보/동작을 정의한다. 동작 없는 클릭을 남기지 않는다.

**검증:** 해지 전 날짜 선택→해지 구독 행 탭→정의한 내용/행동이 실제로 제공된다.

### R2-9. 작은 화면에서 캘린더 7열·카드 여백·48dp 터치 폭을 동시에 만족하기 어렵다

**위치:** S:321, P:888–889, 1063, 1076.

7×48=336dp다. 화면 margin 20dp씩이면 카드 내부 여백을 제외해도 최소 376dp가 필요하다. 360dp 화면이나 작은 멀티윈도에서는 칸마다 48dp 폭을 보장할 수 없다. 현재 테스트는 높이만 검사한다.

**수정:** 최소 창 폭, 좁은 화면에서 여백 축소/대체 레이아웃/스크롤 정책을 정하고, 인접 날짜의 확장 터치 영역이 겹치지 않도록 한다. 48dp 높이만 통과하고 전체 영역을 검증했다고 쓰지 않는다.

**검증:** 320/360dp 창, 가로/분할 화면에서 7열 표시와 각 날짜 탭 판별. 폭·높이 및 실제 인접 셀 hit target을 확인한다.

### R2-10. 2×2 위젯 레이아웃은 있지만 해당 크기로 줄일 provider 설정이 없다

**위치:** P:1253–1257.

Responsive에 110×110을 넣었지만 provider는 minWidth=250dp이고 minResizeWidth가 없다. 런처에서 작은 폭까지 축소 가능한지를 보장하지 못한다. 단위 테스트에서 강제로 110dp를 주는 것은 런처 사용 가능성 검증과 다르다.

**수정:** `minResizeWidth/minResizeHeight`를 작은 레이아웃 지원 범위와 맞추고 기본 4×2 크기와 최소 크기를 구분한다. 그리드 셀 수와 dp가 기기마다 다르다는 점도 반영한다.

**검증:** API 26/33/36 실제 런처에서 추가→작은 크기로 축소→큰 크기로 확대. [공식 위젯 크기 가이드](https://developer.android.com/develop/ui/views/appwidgets/layouts).

### R2-11. 실제 프로세스 복원·저장 실패의 테스트/상태 계약이 부족하다

**위치:** P:986–987, 1117, 1128–1130, 1145, 1172–1175.

같은 SavedStateHandle 객체로 새 ViewModel을 만드는 테스트는 저장→직렬화→새 프로세스에서 복원하는 경계를 검증하지 않는다. ActivityScenario.recreate도 ViewModel이 유지될 수 있어 동일하지 않다. draft만 저장하는 계획에는 신규 DB insert 성공 후 Saved 반영 전에 프로세스가 종료되는 창도 남아 있다. 재진입 후 같은 draft를 저장하면 중복 구독이 될 수 있다. DB 저장 예외는 Outcome 필드 오류에 포함되지 않으며 Saving/busy를 해제할 오류 상태도 명시되지 않았다.

**수정:** 복원 가능한 SavedState registry 데이터로 새 owner/새 handle을 구성하는 테스트와 기기 process-recreation 확인을 구분한다. 저장 도중 종료에 대한 신규 draft 식별자/멱등 저장 또는 허용 정책을 정한다. 저장·해지·삭제 I/O 실패 시 사용자 메시지와 재시도·busy 해제를 정의한다.

**검증:** 입력 draft의 실제 저장/복원, insert commit 후 UI 성공 전 종료, DB 예외 후 입력 보존과 재시도, Cancel/Delete 예외 후 버튼 복구.

## 대응표에 대한 판정과 추가 정정

- 이전 리뷰 #1·#2·#5·#6·#9·#12는 핵심 방향이 반영됐다. 이번 리뷰에서 드러난 관련 경계는 위 R2 항목으로 추적한다.
- #3의 “앱 시작으로 복구” 주장은 R2-1/2/6의 상태 복구가 있어야 성립한다. WorkManager를 안 쓰는 결정 자체는 반박하지 않는다.
- #4의 “단일 사용자·단일 프로세스라 동시 수정 없음”은 충분한 근거가 아니다. suspend 함수·UI·receiver·Application 코루틴은 한 프로세스에서도 겹친다. 내보내기 전체를 원자화하지 않는 절충은 가능하지만, import/recovery와의 충돌은 R2-3으로 막아야 한다.
- #13 predictive back 자동화 생략은 허용 가능한 절충이다. 최소 수동 취소/완료 smoke 항목을 추가하는 편이 목적에 맞는다.
- #15 전이 의존성 라이선스를 모두 Apache-2.0 한 줄로 취급하는 P:1228은 resolved artifact별 라이선스/NOTICE 확인을 대신하지 못한다. 라이브러리 선정 후 실제 목록을 확인하고 묶을 수 있는 항목만 묶는다.
- P:1113·1127·1133은 “나중에”도 실제 OS 권한 요청 이력을 true로 기록한다. 시트 노출과 시스템 요청 실행 이력을 분리한다.
- P:800의 “DB 몇 줄과 알람 등록뿐”과 달리 handler는 refresher를 통해 위젯 갱신까지 await한다. 8초 제한 안에서 반드시 끝난다는 설명은 고치고, timeout 후 예약 진행/재시도를 정의한다.
- P:802 notification id의 Long.hashCode는 충돌 가능하다. 알람의 Long URI와 별개로 notification은 `(tag=subscriptionId 문자열, id=고정값)` 등 충돌 없는 조합을 검토한다.
- P:36의 `git diff`만 리뷰하면 미추적 신규 파일은 나오지 않는다. 새 파일 생성이 대부분인 계획이므로 untracked도 리뷰 대상에 포함하고, staging된 공통 파일을 후속 태스크에서 다시 수정한 경우 전체 최종 diff를 묶음 커밋 전에 재검토한다.

## Claude 전달용 요청

앱 구현에 들어가기 전에 이 재리뷰를 검토하고 **두 원본 문서와 대응표를 갱신해 주세요.** R2-1~R2-11별 수용/부분 수용/반박, 변경 위치, 추가 수용 테스트를 기록해 주세요. 단순히 “Mutex 사용”, “멱등”, “앱 시작 때 복구”라는 문구 추가로 닫지 말고 다음 경계를 의사코드로 보여 주세요.

1. BOOT/기기 복원 시 DB 상태와 실제 OS 예약의 불일치를 복구하는 경로.
2. 수신·예약 변경·취소가 경합할 때 occurrence를 claim/소비하는 경로와 프로세스 종료 시 허용하는 전달 보장.
3. import/recovery 중 UI·편집·수신기·reconcile 접근 게이트와 실패 후 사용자 변경 보존.
4. 미래 시작 취소, 정상 생성 데이터의 백업 왕복, 실제 process restoration 경계.

기존 사용자 결정(사용 구간, 클라우드 백업 제외, 모듈 구성)은 유지하되 변경이 필요하면 제안으로 구분해 주세요. 원본과 대응표가 동일한 계약을 말하도록 맞추고, 아직 구현되지 않은 것을 “검증 완료”로 표시하지 마세요.
