# NextBill v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 반복 결제를 등록하면 다음 결제일·이번 달 합계·알림·위젯·캘린더를 제공하는 오프라인 Android 앱 NextBill v1(F1~F11)을 공개 저장소에 완성합니다.

**Architecture:** Now in Android(커밋 `2982e63`)식 멀티 모듈 + Navigation 3 `api`/`impl` 분리. 도메인 규칙은 JVM 모듈(`core:model`, `core:domain`)의 순수 함수로 두고, 저장·알림·위젯·시간 같은 경계는 `core:domain`에 정의한 인터페이스를 바깥 모듈이 구현합니다(ADR-11). 화면은 Room `Flow` → 도메인 함수 → 불변 `UiState`로 흐릅니다.

**Tech Stack:** Kotlin 2.3, AGP 9.3, Hilt, Jetpack Compose + Material 3, Navigation 3, Room, Preferences DataStore, Glance, kotlinx-serialization-json, JUnit4·Truth·Turbine·Robolectric·Roborazzi, Spotless(ktlint), GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-23-nextbill-design.md` (이하 "설계 문서"). 디자인 원본: `docs/design/stitch/` (`DESIGN.md`, 화면별 `code.html`·`screen.png`).

## Review Focus

1. **시간대 변경·DST:** 사용자가 시간대를 바꾸거나 DST 전환일에 09:00 알림이 있을 때, 알림은 새 시간대의 09:00에 울리고 존재하지 않는 시각(DST gap)은 java.time 규칙대로 뒤로 밀려야 합니다. 시스템 `Clock`이 생성 시점의 zone에 고정되면 깨집니다 → Task 13 `CurrentZoneClock` 테스트, Task 5 DST 테스트.
2. **오늘 알림 시각이 이미 지난 경우:** 결제일 당일 09:00 알림인데 지금 10:00이면 즉시 알림을 띄우지 않고 다음 주기 알림을 예약해야 합니다. `daysBefore`가 주기보다 길 때(매일 결제 + 7일 전)도 "지금 이후 가장 이른 알림"이어야 합니다 → Task 5.
3. **첫 결제일이 미래:** 다음 결제일은 첫 결제일이고, 그 이전 달의 합계·캘린더에는 결제가 없어야 합니다(음수 n 생성 금지) → Task 3, Task 4.
4. **잘못된·새 버전·빈 백업 파일:** 깨진 JSON, `schemaVersion`이 더 큰 파일, 구독 0개 파일. 앞의 둘은 데이터를 건드리지 않고 오류를 알리고, 마지막은 정상 교체입니다. 교체 시 **사라진 구독의 알림도 취소**돼야 합니다 → Task 8, Task 12.
5. **금액 입력:** 빈 값, 0, `1,000` 같은 쉼표, KRW에 `1.5`, USD에 `9.999`, JPY, 매우 큰 값. 월 환산(일 주기 ×365)에서 `Long` 오버플로가 나면 안 됩니다 → Task 4(BigDecimal), Task 6(상한 `MAX_MINOR = 1_000_000_000_000`).

### Task 2: 모듈 의존 규칙 검사 (`checkModuleRules`)

**Files:**
- Create: `build-logic/convention/src/main/kotlin/ModuleRulesPlugin.kt`, `build-logic/convention/src/main/kotlin/io/github/alexdhkim/nextbill/ModuleRules.kt`
- Test: `build-logic/convention/src/test/kotlin/ModuleRulesTest.kt`
- Modify: 루트 `build.gradle.kts` (`id("nextbill.module-rules")`)

**Interfaces:**
- Produces: `fun violations(edges: Map<String, Set<String>>): List<String>` — 키는 모듈 경로(`:feature:home:impl`), 값은 그 모듈이 의존하는 프로젝트 경로들. 규칙 위반 메시지 목록을 반환합니다. 루트 태스크 `checkModuleRules`는 모든 서브프로젝트의 `api`/`implementation` 설정에서 `ProjectDependency`를 모아 이 함수에 넘기고, 결과가 비어 있지 않으면 실패합니다.

규칙(설계 문서 §5.2):
1. `:core:model`은 프로젝트 의존 0개.
2. `:core:domain`은 `:core:model`만.
3. `:feature:*:impl`은 다른 feature의 `impl`을 의존하지 않음.
4. `:core:database`, `:core:datastore`는 `:core:data`(와 각자의 테스트)만 의존할 수 있음. 즉 `:core:data` 외 모듈이 이 둘을 의존하면 위반.
5. `:feature:*`는 `:core:data`를 의존하지 않음(앱만 조립).

- [ ] **Step 1: 실패하는 테스트 작성**

```kotlin

}
@Test fun domainMayDependOnlyOnModel() {
    assertThat(violations(mapOf(":core:domain" to setOf(":core:model")))).isEmpty()

@Test fun onlyDataMayDependOnDatabaseAndDatastore() {

}
@Test fun featureMustNotDependOnData() {
    assertThat(violations(mapOf(":feature:home:impl" to setOf(":core:data")))).hasSize(1)
}
@Test fun featureImplMayDependOnOtherFeatureApi() {
    assertThat(violations(mapOf(":feature:home:impl" to setOf(":feature:editor:api", ":feature:detail:api")))).isEmpty()
}
```
