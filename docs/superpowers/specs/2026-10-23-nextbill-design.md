## 1. 왜 만드는가

### 1.1 배경
Alex는 14년차 Android 개발자로, 다시 **Android 개발자**로 취업하려고 합니다. 2026-10 토스·당근 서류 검토(hiring-panel)에서 확인한 공백은 세 가지입니다.
- Jetpack Compose 실무 결과물이 없음
- 2025.03 이후 네이티브 Android 작업 비중이 줄어듦
- AI 활용이 "본인 설계"인지 "AI가 만든 결과"인지 구분되지 않음

NextBill은 이 공백을 **공개적으로 확인 가능한 결과물**로 메우기 위한 포트폴리오 앱입니다.

### 1.2 면접관이 알아차려야 할 것 [Alex 결정]
1. **AI를 잘 다루되, 바이브코딩이 아니라 설계가 먼저였다.** 설계 문서·결정 기록(ADR)이 코드보다 먼저 커밋되어 있고, AI를 통제하는 규칙과 검증 장치가 저장소에 드러나 있어야 합니다.
2. **트렌드에 뒤처지지 않는다.** Now in Android 최신 구조 수준의 모듈화, 클린 아키텍처, Hilt, Compose를 씁니다.
3. **불필요한 라이브러리를 쓰지 않는다.**
4. **객체지향과 함수형을 필요한 곳에 나눠 쓴다.** 역할과 책임은 객체지향으로 명확히 하고, 규칙과 데이터 흐름은 Kotlin 함수형으로 구현합니다.

### 1.3 성공 기준
- 면접관이 저장소 첫 화면(README)만 보고 위 4가지를 읽을 수 있습니다.
- Alex가 저장소의 모든 설계 결정과 핵심 코드를 **AI 없이 설명할 수 있습니다.** 이것이 안 되면 실패입니다.
- 이력서 기술 칸을 "Jetpack Compose: 개인 프로젝트로 구현(링크) · 실무 운영 경험 없음"으로 바꿀 수 있습니다.

### 1.4 기술적으로 동작해도 실패인 것 (anti-goals)
- Now in Android를 그대로 복사한 것처럼 보이는 것
- 라이브러리를 쌓아 올린 것
- Alex가 설명하지 못하는 코드가 섞인 것
- **전 직장(museLIVE/Quabble)의 설계·코드·문서·규칙 파일을 재현하거나 참고한 것.** 퇴직자 비밀유지서약서(2026-10-08 서명) 1조·5조의 "노하우", "시스템 설계", "업무상 성과물과 아이디어"와 충돌할 수 있습니다. AI 검증 체계도 백지에서 새로 작성합니다.

## 2. 제품

### 2.1 한 줄 정의
넷플릭스, 통신비, 보험료처럼 **반복되는 결제를 등록하면 다음 결제일을 알려 주고, 이번 달에 얼마가 나가는지 보여 주는** Android 앱입니다.

### 2.2 원칙
- **서버 없음 [Alex 결정].** 모든 데이터는 기기 안에만 저장합니다. "금융 데이터는 기기 밖으로 나가지 않는다"를 README와 ADR에 설계 원칙으로 씁니다.
  - 이 원칙에 맞춰 **Android 클라우드 자동 백업(Google Drive)은 끄고, 기기 간 직접 전송(device-to-device)만 허용**합니다 [Alex 결정, 2026-10-24, ADR-8].
  - 예외는 사용자가 직접 고른 경우뿐입니다. 백업 파일을 내보낼 때 사용자가 클라우드 문서 앱을 저장 위치로 고르면 그곳에 저장됩니다. README에 이 차이를 씁니다.
- **로그인 없음, 네트워크 권한 없음 [설계자 판단].** `INTERNET` 권한을 선언하지 않는 것 자체를 원칙의 증거로 보여 줍니다.

## 4. 도메인

### 4.1 모델 (`core:model`, 순수 Kotlin)
```kotlin
@JvmInline value class SubscriptionId(val value: Long)

data class Money(val minor: Long, val currency: CurrencyCode) // 최소 단위 정수(원, 센트). 부동소수점 금지

@JvmInline value class CurrencyCode(val value: String)        // ISO 4217

sealed interface BillingCycle {
    val interval: Int                                         // ≥ 1
    data class Days(override val interval: Int) : BillingCycle
    data class Weeks(override val interval: Int) : BillingCycle
    data class Months(override val interval: Int) : BillingCycle
    data class Years(override val interval: Int) : BillingCycle
}

data class Reminder(val enabled: Boolean, val daysBefore: Int, val time: LocalTime)

enum class SubscriptionStatus { ACTIVE, CANCELLED }

data class ActivePeriod(val start: LocalDate, val end: LocalDate?) // 사용 구간. end = 해지일(포함), null = 사용 중

data class Subscription(
    val id: SubscriptionId,
    val name: String,
    val price: Money,
    val cycle: BillingCycle,
    val anchorDate: LocalDate,      // 첫 결제일 = 결제일 계산의 기준
    val category: Category,
    val colorKey: ColorKey,
    val memo: String,
    val reminder: Reminder,
    val periods: List<ActivePeriod>, // 비어 있지 않음, 시간순, 겹치지 않음, 마지막만 열려 있을 수 있음
) {
    val status: SubscriptionStatus   // 마지막 구간이 열려 있으면 ACTIVE
    val cancelledAt: LocalDate?      // 마지막 구간의 end
}
```
위 코드는 모양을 보여 주기 위한 스케치입니다. 이름과 세부 필드는 구현하는 사람이 정합니다. 다만 **불변, value class, 정수 금액, sealed 주기**라는 원칙은 유지해야 합니다.

### 4.2 결제일 규칙 (`core:domain`, 순수 함수) — 이 앱의 핵심 테스트 대상
- **n번째 결제일 = 기준일 + (주기 × n)** 으로 계산합니다. 직전 결제일에 주기를 더해 나가는 방식은 쓰지 않습니다. 예를 들어 1/31 기준 월 결제가 2/28 → 3/28로 밀려 버리는 누적 오차를 막기 위해서입니다.
- **월말 보정:** 해당 월에 그 날짜가 없으면 그 달의 마지막 날로 맞춥니다. 1/31 기준이면 2/28(윤년은 2/29) → 3/31 → 4/30입니다. 연 주기에서 2/29 기준이면 평년에는 2/28입니다.
- **다음 결제일:** `today` 이상인 가장 이른 결제일입니다. 결제일이 오늘이면 다음 결제일은 오늘입니다.
- **사용 구간 [Alex 결정, 2026-10-24]:** 결제는 `anchorDate + 주기 × n` 중 **어떤 사용 구간(`periods`) 안에 드는 날짜**만 발생한 것으로 봅니다. 구간의 시작일·종료일은 모두 포함합니다. 첫 구간의 시작일은 항상 `anchorDate`입니다.
- **해지:** 마지막 구간의 `end`를 해지한 날로 닫습니다. 해지일 **이전·당일의 결제는 이미 발생한 것**으로 보고 합계와 캘린더에 남깁니다. 이후 결제는 없고, 다음 결제일도 알림도 없습니다.
- **첫 결제 전 구독 [Alex 결정, 2026-10-24 2차 리뷰]:** 구간이 하나뿐이고 `anchorDate`가 오늘 이후이면 아직 결제가 한 번도 없으므로 해지할 수 없습니다. 상세 화면은 "해지 처리" 대신 "삭제"만 보여 주고 "아직 첫 결제 전이라 기록 없이 삭제돼요"라고 안내합니다. 시스템 날짜를 되돌려 **마지막 구간이 아직 시작 전**인 상태에서 해지하면(구간 2개 이상), 그 구간을 지우고 직전 구간의 해지 상태로 돌아갑니다.
- **복원:** 복원한 날을 시작일로 새 구간을 엽니다. 해지 기간의 결제는 과거 달 캘린더와 합계에도 나타나지 않습니다(소급 없음). 복원일이 마지막 해지일 다음 날 이하이면 새 구간을 만들지 않고 마지막 구간을 다시 엽니다. 같은 날 결제가 두 번 세어지지 않게 하기 위해서입니다.
- **한도 [Alex 결정, 2026-10-24 2차 리뷰]:** 구독은 최대 1,000건, 구독마다 사용 구간은 최대 50개입니다. 한도에 닿으면 등록·다시 사용 때 "더 이상 추가할 수 없어요"를 보여 줍니다. 첫 결제일은 1900-01-01~2200-12-31입니다. 앱이 만들 수 있는 모든 상태는 백업 파일로 내보내고 다시 가져올 수 있어야 합니다(ADR-7).
- **수정의 범위:** 금액·주기·통화를 바꾸면 **과거 달도 새 값으로 다시 계산**합니다. 금액 변경 이력은 v1 범위 밖입니다. 기준일을 바꾸면 첫 구간의 시작일도 같이 바뀝니다. 해지한 구독은 수정할 수 없고, 복원한 뒤 수정합니다.
- **삭제:** 과거 기록까지 모두 지웁니다(합계에서도 사라짐). 기록을 남기려면 해지를 씁니다.
- **이번 달 결제 예정 합계:** 이번 달(1일~말일, 기기 시간대) 안에 들어가는 모든 결제일의 금액 합계입니다. 주 주기는 한 달에 4~5회입니다. 이미 지난 날짜도 이번 달이면 포함합니다. 통화별로 따로 합산합니다.
- **월 환산 고정비:** 일 주기 `금액 × 365 / 12 / N`, 주 주기 `금액 × 365 / 7 / 12 / N`(일 주기와 같은 365일 기준. 화면에는 "환산"으로 표시해 추정값임을 드러냅니다), 월 주기 `금액 / N`, 연 주기 `금액 / 12 / N`. 정수 최소 단위로 계산하고 반올림 규칙(HALF_EVEN)을 한 곳에서 정의합니다.
- **알림 시각:** `다음 결제일 − daysBefore`의 `reminder.time`(기기 시간대 기준)입니다. 알림은 **결제일 하나(occurrence)에 묶어** 예약하고, 받을 때는 예약된 결제일로 안내합니다. 예약할 occurrence는 구독마다 DB에 기록하고, OS에는 가장 이른 시각의 알람 하나만 겁니다(ADR-3·4).
- **오늘 날짜:** 화면은 날짜 변경·시간 변경·시간대 변경·앱 복귀 때 오늘 날짜를 다시 받아 재계산합니다(ADR-12).
- 시간은 `java.time.Clock`을 주입받아 계산합니다. 테스트에서 오늘 날짜를 고정할 수 있게 하기 위해서입니다.

### 4.3 객체지향과 함수형의 분배 [Alex 방향 + 설계자 구체화]
| 영역 | 방식 | 구현 |
|---|---|---|
| 도메인 규칙 (결제일, 합계, 환산) | **함수형** | 부수효과 없는 최상위 함수 또는 `object`. 입력은 불변 값, 출력은 새 값입니다. 결제일은 `generateSequence`로 지연 생성합니다 |
| 경계 (저장, 알림 예약, 위젯 갱신, 시간) | **객체지향** | `SubscriptionRepository`, `ReminderAlarm`, `ReminderPoster`, `WidgetUpdater`, `Clock` 인터페이스와 구현. Hilt로 조립합니다 |
| 화면 상태 | **함수형** | Room `Flow` → `combine`·`map` → 불변 `UiState`(sealed). ViewModel은 상태를 소유만 하고 계산은 도메인 함수에 위임합니다 |
| 사용자 액션 | **객체지향 + 함수형** | ViewModel의 의도별 메서드가 UseCase를 호출합니다. 유효성 검사는 `Either`류 sealed 결과 타입으로 반환합니다(별도 라이브러리 없이 직접 정의) |

**성능에 대한 설계 의도 (README에는 "의도"로만 씁니다):** 함수형으로 썼다고 자동으로 빨라지지는 않습니다. 이 앱에서 의도한 지점은 세 가지입니다.
1. 불변 UI 모델로 Compose가 불필요한 recomposition을 건너뛸 수 있게 합니다.
2. Sequence 지연 계산으로 필요한 결제일만 생성합니다.
3. 무거운 계산을 `Dispatchers.Default`로 보냅니다.

Compose 컴파일러 리포트는 **안정성(stable 여부)만** 보여 주고 속도를 증명하지 않습니다. `@Immutable`은 리포트를 통과시키는 수단으로 쓰지 않습니다. 실제 성능 개선을 주장하려면 release 빌드에서 측정한 근거(trace, benchmark)가 있어야 하고, 측정하지 않았으면 쓰지 않습니다.

### 5.2 의존 규칙 (빌드가 강제)
- `core:model`과 `core:domain`은 **Android 의존성 0개**(JVM 모듈)입니다. `core:domain`은 `core:model`만 의존합니다.
- `feature:*:impl`은 다른 feature의 `impl`을 의존하지 않습니다. 화면 이동은 상대 feature의 `api`(NavKey)로만 합니다.
- `core:data`만 `core:database`·`core:datastore`를 압니다. feature는 Repository 인터페이스(`core:domain`에 정의)만 압니다.
- 이 규칙은 convention plugin과 모듈 의존 검사(Gradle 태스크 또는 테스트)로 강제하고, `CLAUDE.md`에도 같은 규칙을 씁니다.

### 5.3 convention plugin [설계자 판단]
`android.application`, `android.application.compose`, `android.library`, `android.library.compose`, `android.feature.api`, `android.feature.impl`, `android.room`, `hilt`, `jvm.library`, `android.test`. 약 10개이며, 필요해질 때만 추가합니다.

| ADR-13 | **데이터 저장과 파생 상태 갱신을 분리**합니다. 저장·해지·복원·삭제는 DB에 반영되면 성공입니다. 알림 재예약과 위젯 갱신은 앱 범위 코루틴에서 따로 실행하고, 실패해도 저장 결과를 바꾸지 않습니다. 가져오기와 앱 시작도 같습니다. 데이터 교체·복구가 확정된 뒤의 알람 갱신 실패는 가져오기 성공이나 준비 상태를 바꾸지 않고, 알람은 다음 갱신이 다시 겁니다 [2026-10-25 4차 리뷰]. 갱신은 한 번에 하나씩 실행하고, 실행 중에 요청이 오면 끝난 뒤 최신 데이터로 한 번 더 실행합니다. 프로세스가 죽어도 새 프로세스의 첫 갱신이 OS 알람을 다시 걸므로 복구됩니다(ADR-4). 실패를 삼킬 때도 코루틴 취소(`CancellationException`)는 삼키지 않습니다. 저장 자체가 실패하면(DB 예외) 화면은 "저장하지 못했어요"를 보여 주고 입력을 그대로 둡니다. **허용한 위험:** 저장이 DB에 반영된 직후, 화면이 결과를 받기 전에 프로세스가 죽으면 복원된 입력으로 다시 저장해 같은 구독이 2건 생길 수 있습니다. 막지 않으며, 발생 빈도는 측정하지 않았습니다 | 갱신이 실패했을 때 저장까지 실패로 보이면 다시 저장을 눌러 중복 저장이 생깁니다. 별도 작업 큐(WorkManager)는 앱 시작 갱신으로 충분해 쓰지 않습니다 |
| ADR-14 | **알림 전달은 best effort**입니다 [2026-10-24 3차 리뷰로 "최소 1회" 문구 철회]. 알림이 오지 않을 수 있는 경우: OS가 알람을 늦추거나 지운 뒤 앱이 다시 시작되지 않음, 알림 권한·채널 차단, 결제일이 지난 뒤 처리됨, 처리 중 시간 초과. 알림을 게시한 뒤 기록을 소비하기 전에 처리가 끊기면 같은 occurrence가 다음 처리 때 다시 게시될 수 있고, 횟수 상한은 두지 않습니다. 같은 구독의 알림은 고정 tag로 대체되어 화면에는 하나만 남습니다. **화면에 남아 있는 알림과 새 알림을 합쳐 4건 이상이면 묶음 알림 하나**로 보여 주고(3건 이하는 각각), 사용자가 지운 알림은 되살리지 않습니다(다만 앱이 화면을 읽은 직후에 지운 알림은 다음 게시 때 다시 보일 수 있습니다. 사용자 동작은 앱의 잠금으로 막을 수 없습니다). 그래서 화면의 앱 알림은 항상 3개 이하이고, 전체 내역은 홈 화면에서 봅니다. 결제일이 지난 알림은 갱신 때 지웁니다 [Alex 결정, 2026-10-24 3차 리뷰 → 2026-10-25 4차 리뷰에서 기준을 '한 번의 처리'에서 '화면 전체'로 바꿈] | DB와 OS 알림을 한 트랜잭션으로 묶을 수 없습니다. 놓치는 것보다 다시 오는 쪽이 결제 알림에 맞습니다. Android 12 AOSP `NotificationManagerService`는 앱이 띄운 알림이 50개(`MAX_PACKAGE_NOTIFICATIONS = 50`)에 닿으면 더 보여 주지 않습니다. 알림이 하나씩 따로 와도 화면에 쌓이면 일부가 조용히 사라지므로, 화면 전체를 기준으로 묶고 정리합니다 |

### 9.2 화면 품질 기준 [설계자 판단, 2026-10-24 리뷰 반영]
태블릿 전용 레이아웃은 v2지만, 아래는 v1에서 지킵니다. 자동 검증과 직접 확인을 나눕니다.
- **자동:** 글꼴 200% 스크린샷(홈·등록), 터치 영역 48dp 이상(칩·스와치; 캘린더 날짜는 **창 폭 360dp 이상**에서 폭·높이 모두 48dp — 그보다 좁은 창은 7등분 폭을 쓰고 이웃 칸과 터치 영역이 겹치지 않음), 캘린더 날짜의 접근성 설명("11월 15일, 결제 2건, 선택됨"), D-n 칩은 색 말고 글자로도 구분.
