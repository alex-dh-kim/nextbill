# ADR-0007: 백업은 버전 필드가 있는 JSON, 가져오기는 검증 후 전체 교체

- 상태: 승인 (2026-10-23), 2~5차 리뷰(2026-10-24~25) 반영
- 출처: 설계 문서 §4.2 한도, §6 ADR-7 [설계자 판단]

## 맥락
- 서버가 없으므로(ADR-0001) 기기를 바꾸거나 데이터를 옮길 방법은 백업 파일과 기기 간 전송(ADR-0008)뿐입니다.
- Room(구독)과 DataStore(설정)는 하나의 트랜잭션으로 묶을 수 없습니다. 가져오기 도중 프로세스가 죽으면 한쪽만 바뀐 상태가 남을 수 있습니다.
- 가져오기가 끝나기 전이나 실패한 뒤에 사용자가 편집한 내용이 조용히 덮이면 안 됩니다.

## 결정
- **형식:** 버전 필드가 있는 JSON(`schemaVersion`). 구독(사용 구간 포함)과 설정을 모두 포함합니다. 직렬화는 kotlinx-serialization-json을 씁니다.
- **가져오기는 전체 교체**이고, 실행 전 확인 대화상자를 띄웁니다. 교체 전에 파일 전체를 검증합니다(크기·건수·값 범위·구간 규칙). 파일의 id는 버리고 새로 매깁니다.
- **수렴:** 검증한 내용을 임시 파일에 먼저 쓰고 DB·설정에 적용한 뒤 지웁니다. 앱 시작 때 임시 파일이 남아 있으면 다시 적용해 "전부 이전" 또는 "전부 새것"으로 수렴시킵니다. 예외: 복구 화면에서 "가져오기 취소"를 고르면 구독은 새것·설정은 이전 것처럼 일부만 바뀐 상태가 남을 수 있고, 확인 문구로 알립니다.
- **적용이 끝나기 전에는 편집할 수 없습니다:** 앱 시작 상태(`Recovering → Ready | RecoveryFailed`)가 Ready가 될 때까지 시작 화면을 유지합니다. 적용이 한 번 다시 시도해도 실패하면 전체 화면에서 "다시 시도"·"가져오기 취소"를 고르게 합니다.
- **같은 잠금:** 가져오기 적용과 저장·설정 변경·알림 처리·지난 알림 정리는 같은 잠금을 씁니다. 복구 실패를 확인한 뒤의 알람 취소도 그 잠금 안에서 합니다. 잠금을 얻은 뒤 준비 상태와 데이터 세대를 다시 확인해, 복구 중·복구 실패 뒤의 쓰기와 가져오기 전에 연 화면의 쓰기는 거부합니다.
- **데이터 세대:** DB에 영속 저장하고 전체 교체와 같은 트랜잭션에서 올립니다. 프로세스가 다시 만들어져 화면 기록과 입력이 복원돼도 같은 기준으로 비교됩니다.
- 앱 시작 직후 먼저 온 알림 처리는 복구가 끝날 때까지 기다립니다.
- 임시 파일 쓰기부터 적용·삭제·세대 갱신까지는 코루틴 취소로 끊기지 않게 실행합니다. 임시 파일 쓰기·삭제 실패는 파일 시스템 결과로 확인하고, 삭제가 확인되기 전에는 성공으로 보지 않습니다. 삭제에 실패하면 복구 화면으로 갑니다.
- 가져온 뒤에는 모든 탭의 화면 기록을 처음으로 되돌립니다(id가 새로 매겨지므로).
- 파일 크기 한도는 §4.2 한도(구독 1,000건, 구독당 구간 50개) 안의 최대 상태를 담을 수 있게 정합니다. 앱이 만들 수 있는 모든 상태는 내보내고 다시 가져올 수 있어야 합니다.

## 대안
- **병합 가져오기:** 충돌 규칙이 필요해 v1 범위를 넘습니다.
- **구독만 백업:** 기기를 바꿀 때 설정이 사라집니다.
- **임시 파일 없이 바로 적용:** 적용 도중 프로세스가 죽으면 Room과 DataStore 중 한쪽만 바뀐 상태가 남습니다.

## 결과
- 잘못된 파일은 아무것도 바꾸지 않습니다. 단계별 실패 주입 후 재시작 시 한쪽 상태로 수렴하는지 테스트합니다(설계 문서 §8 백업·가져오기 관문).
- 한도 안 최대 상태의 왕복(`decode(encode(s)) == s`)을 테스트합니다.
- 가져오기 임시 파일(`files/import-staging.json`)은 기기 간 전송·백업 규칙 어디에도 포함하지 않습니다(ADR-0008).
