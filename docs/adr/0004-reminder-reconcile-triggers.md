# ADR-0004: 알림 예약은 전부 다시 걸지 않고 바뀐 것만 고칩니다(reconcile)

- 상태: 승인 (2026-10-23), 2~4차 리뷰(2026-10-24~25) 반영
- 출처: 설계 문서 §6 ADR-4 [설계자 판단]

## 맥락
- 재부팅·강제 종료는 OS 알람을 지우지만 DB 기록은 남깁니다. 강제 종료를 알려 주는 브로드캐스트는 없습니다.
- "전부 취소 후 재예약"을 하면 Doze로 늦어지고 있던 다른 구독의 알림이 사라집니다.
- OS 알람은 하나뿐이므로(ADR-0003) 그 하나를 언제 다시 걸지 정해야 합니다.

## 결정
- 갱신 트리거: `BOOT_COMPLETED`, `TIME_SET`, `TIMEZONE_CHANGED`, `MY_PACKAGE_REPLACED`, 앱 시작 시, 구독 저장·해지·복원·삭제·가져오기 후.
- 갱신은 **전부 취소하지 않고**, DB의 예약 기록을 바뀐 구독만 고칩니다. 시각이 지났지만 아직 처리하지 않은 기록은 보존합니다. 그다음 OS 알람을 가장 이른 기록 시각에 맞춥니다.
- 같은 프로세스 안에서는 그 시각(지났어도 원래 예정 시각으로 비교)이 바뀔 때만 다시 겁니다. **프로세스가 새로 시작된 뒤 첫 갱신은 무조건 다시 겁니다.**
- 알람이 울리면 시각이 지난 기록을 한 번에 처리하고 다음 알람을 겁니다.
- 예약 기록은 OS 알람보다 먼저 씁니다.
- 갱신과 알림 처리는 같은 잠금 안에서 한 번에 하나씩, 앱이 준비 상태일 때만 실행합니다(ADR-0007).

## 대안
- **전부 취소 후 재예약:** 단순하지만 늦어지고 있던 알림을 잃습니다.
- **PendingIntent 존재 여부로 등록 상태 판단:** 재부팅·강제 종료 뒤의 상태를 믿을 수 없어 쓰지 않습니다(2차 리뷰 대응).

## 결과
- 재부팅·강제 종료·기기 전송 뒤에도 프로세스 시작 때의 첫 갱신으로 복구됩니다.
- 바뀌지 않은 기록은 건드리지 않고, 예정 시각이 지난 알람을 이후 갱신이 다시 걸지 않는다는 것을 테스트로 확인합니다(설계 문서 §8).
- 같은 프로세스 안에서 OS 등록이 실패하면 다음 갱신이 다시 시도합니다.
